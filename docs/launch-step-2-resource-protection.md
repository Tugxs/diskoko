# الخطوة الثانية: حماية الطلبات والذاكرة والعمل المكلف

هذه الدفعة تعالج محور حماية الموارد في تقرير الإطلاق. لا تغيّر خطة Render أو محرك AI أو صلاحيات العملاء، ولا تعيد محاولة تغييرات Discord تلقائيًا. تحديد عدد العملاء والرفع الفعلي للسعة في الخطوة التاسعة؛ الحدود التالية سقوف حماية محافظة وليست وعدًا بالأداء.

## ترتيب الحماية

1. رؤوس الأمان ومعرّف الطلب، ثم gate محلي محدود قبل الجلسة وقبل قراءة JSON.
2. الجلسات لمسارات API وOAuth والإدارة فقط. الملفات والصفحات العامة لا تستعلم عن جلسة العميل حتى لو حمل الطلب cookie؛ فحص الصحة له مسار محدود مستقل دون جلسة.
3. CSRF ومصدر الطلب قبل تحليل المحتوى. إعفاءات webhook الموقّع والعامل الموثق تبقى كما هي، مع حدود استقبال محلية وحجم طلب.
4. الرفع الكبير يحتاج حسابًا مسجلًا نشطًا. حدود الحساب والأعمال المتزامنة تؤخذ من PostgreSQL قبل قراءة المحتوى، وتُرفض الطلبات الجديدة عند تعذر فحصها.
5. JSON غير مضغوط فقط؛ سقف قياسي 512 KiB، و29 MiB لمسارات الوسائط السابقة المحددة بدقة. لا يمكن اختيار السقف الكبير بتغيير query أو عبر مسار غير معروف. الطلب chunked يظل خاضعًا لسقف parser ومهلة الاستقبال وحجز الوسائط.
6. الصلاحيات واشتراكات الأدوات ومراجعات التنفيذ السابقة تبقى بعد parsing؛ الحصول على حجز موارد لا يمنح صلاحية عمل.

## السياسات الحالية

| الطبقة | الحد الافتراضي |
|---|---|
| مصدر الشبكة | token bucket: اندفاع 120 طلبًا وتجدد 10/ثانية، عبر جميع الروابط؛ IPv6 يجمع ضمن /64، وIPv4-mapped يعود إلى IPv4 |
| الخدمة المحلية | اندفاع 160 وتجدد 40/ثانية؛ 48 طلبًا متزامنًا كحد أقصى |
| الأعمال المكلفة المحلية | 6؛ عملية واحدة مشتركة بين الرفع الكبير وتنزيل المرفقات/التصدير |
| الصحة | ميزانية مستقلة: اندفاع 20 وتجدد 5/ثانية، حتى 4 طلبات متزامنة؛ ليست بوابة غير محدودة |
| سجل المصادر | 10 آلاف مفتاح كحد أقصى لكل limiter، TTL وتنظيف تدريجي محدود؛ لا مفتاح لكل URL عشوائي |
| الحساب عبر النسخ | 240 طلب API/دقيقة، و12 طلبًا متزامنًا، وعملان مكلفان متزامنان |
| الفئات المشتركة | توليد طلب AI: 12/دقيقة؛ كود وتنزيل: 30 لكل فئة؛ وسائط: 12؛ كتابة عامة: 60 |
| الفئات المكلفة عبر نسخ الويب | 6 أعمال، وحجز ذاكرة واحد للرفع الكبير أو التنزيل |
| حجم استقبال فئة الوسائط | 64 MiB/دقيقة للحساب و128 MiB/دقيقة للخدمة؛ يحجز الحجم المعلن أو السقف الكامل عند عدم إعلانه |
| حجز قاعدة فحص الموارد | 8 محاولات DB معلقة كحد أقصى، مهلة أقفال 250 ms وstatement 2 s داخل transaction؛ اتصال pool مهلة 3 s |
| الاستقبال | مهلة body مضبوطة 60 s، وNode requestTimeout=65 s، headersTimeout=15 s، keepAlive=5 s، 100 طلب لكل socket |

الحدود المحلية per-process، والحسابات والأعمال المكلفة وحجم رفعها مشتركة بواسطة PostgreSQL. سقوف الحساب تستخدم نوافذ دقيقة ثابتة حسب ساعة قاعدة البيانات؛ قد تسمح النافذة باندفاع عند الحد الفاصل، وتمنعه حدود التزامن/الـtoken bucket من التحول إلى عمل غير محدود. هذه ليست قائمة منع نهائي للمستخدم.

التزامن المرتفع جدًا أو DB المشغولة يعيدان 503 قبل بدء العمل، وحد الحساب يعيد 429، مع Retry-After ورمز مفهوم. لا تضاف طلبات إلى طابور انتظار HTTP غير محدود، ولا تعاد الكتابة تلقائيًا. حدود المراجعة وعدم التكرار للأعمال تبقى مستقلة.

## الحجوزات والتعطل

- resource_rate_buckets وresource_request_leases لا تحفظ أجسام الطلبات أو الأسرار أو عناوين IP أو URLs؛ owner مخزن كتجزئة.
- قرارات الحساب تتم تحت أقفال transaction قصيرة، مع قفل مشترك للأعمال الثقيلة حتى لا تتجاوز نسختان الحد بالتسابق.
- الحجز ينتهي خلال دقيقتين عند موت العملية، ويتجدد كل 20 ثانية ما دامت المعالجة نشطة. التنظيف محدود الدفعة، وإطلاق الحجوزات idempotent، وإعادة محاولة إطلاقها مجمعة ومحدودة الذاكرة.
- فصل العميل بعد إرسال عمل مكلف لا يحرر مكانه فورًا لبدء عمل آخر. يبقى الحجز حتى إكمال استجابة المعالج، أو حد احتفاظ محافظ خمس دقائق عند انقطاعه. لا يعني قطع اتصال المتصفح إلغاء أثر خارجي بدأ بالفعل.
- عند تعطل قاعدة فحص الموارد تُرفض admissions الجديدة، ولا يُتجاوز الضابط. انتهاء lease ليس قفل أعمال أو ضمان exactly-once؛ انقطاع طويل للقاعدة والعمل الخارجي يحتاج اختبارات الأعطال والأقفال التجارية في الخطوتين 6 و9.
- الرفض قبل اكتمال رفع المحتوى يغلق الاتصال بعد تصريف رسالة الرفض بمهلة قصيرة، بدل استمرار تفريغ upload غير محدود. يشمل رفض الجلسة/CSRF، وليس gate الضغط وحده.

## حماية التخزين

التنزيل يعامل كعمل مكلف وحجز ذاكرة، مع تحرير فوري عند فصل العميل؛ لا يخضع لبوابة امتلاء التخزين الخاصة بالكتابة.

قبل الكتابة المكلفة يُفحص pg_database_size، مع هامش ثلاث مرات حجم الطلب. الحد اللين الحالي 700 MiB، مناسب كبداية لقرص الإنتاج الحالي 1 GB، ويضبط عبر RESOURCE_DB_SOFT_LIMIT_MB بعد مراجعة سعة القرص. قيمة غير صالحة تمنع التشغيل بدل تعطيل الحماية بصمت.

عند بلوغ الهامش تتوقف الكتابات الجديدة المكلفة بـSTORAGE_PRESSURE، وتبقى القراءات والخروج وطلبات الإلغاء/الحذف متاحة وفق صلاحياتها. بوابة webhook والعامل لا تتحول إلى كتابة عميل غير موثقة.

pg_database_size ليس قياسًا لكل WAL/النسخ الاحتياطي أو مساحات المنصة، ولا يقيّد جميع الكتابات الخلفية. يبقى رصد القرص والتوسعة والاحتفاظ والتعافي ضمن خطوات قاعدة البيانات والتشغيل؛ هذا هامش مبكر لا ضمان أن القرص يستحيل أن يمتلئ.

## الصور والأكواد

- Sharp: كاش native مقداره 16 MiB، ملفات cache=0، خيط libvips واحد. هذا حد الكاش لا حد RSS الكلي.
- عمليات توليد صور البطاقات ودمج GIF والمؤثرات تعمل بعملية native واحدة منتظَرة منطقيًا لكل process، وطابور طلبين فقط بمهلة انتظار ثانيتين. الضغط يعود IMAGE_BUSY بدل تراكم وعود وبفرات بلا حد.
- كاش كل من صور الموسيقى والمجتمع محدد بـ8 MiB و64 عنصرًا، مع TTL وإخلاء LRU؛ عدد العناصر وحده لم يكن كافيًا.
- تنزيل الصور محدود streaming حتى عند غياب أو عدم دقة Content-Length؛ لا تنزيل الجسم كاملًا ثم اكتشاف أنه كبير. إدخال الصور الثابتة محدد بـ16 مليون بكسل.
- GIF بدمج صورة العضو له سقف 16 مليون بكسل للإطار، مع حدود المصدر السابقة. الإخراج يختار حتى 24 إطارًا ويحافظ على مجموع التأخير؛ لا يتراكم 100 إطار بحجم 1200×480 في الناتج. قد تقل سلاسة GIF الطويل بعد الدمج، ولا يتغير الملف الأصلي أو عرضه دون الدمج.
- تنفيذ الكود يبقى بحد عمليتين معزولتين لكل process، لكن الحساب الواحد لا يشغل الاثنتين بتبديل السيرفر/البوت. تبقى حدود QuickJS والوقت والذاكرة وRPC، ويحرر الحجز عند نجاح/فشل إنشاء العملية أو انتهائها. هذا ليس توزيع Gateway أو زيادة سعة الموسيقى؛ لها قياس مستقل لاحقًا.

## الرصد والاختبارات

GET /api/admin/resource-pressure محمي بحارس إدارة الموقع الحديث. يعرض عدادات الرفض والحجوزات والطابور وRSS/heap دون معلومات عميل أو توكنات. المراقبة التاريخية والتنبيهات في خطوة الرصد، ولا ندّعي أن عداد RAM المحلي يبقى بعد إعادة التشغيل.

- اختبارات HTTP حقيقية محلية: تجاوز الحجم والترميز، chunked، الرفع المجهول، timeout، تزامن ورفض قبل parsing، بقاء الصحة متاحة، إطلاق الحجز، فصل العميل، وتعطل DB وفصل ملفات الموقع عن جلساته.
- اختبارات الذاكرة: 600 ألف مفتاح اصطناعي؛ بقي السجل عند 10000، والـheap بعد GC نحو 8 MiB في بيئة الفحص، وكاش الصور بقي عند 8 MiB. يعاد تشغيلها بواسطة `node --expose-gc scripts/check-resource-bounds.mjs`. هذه ليست حركة إنتاج أو إثبات سعة عملاء.
- اختبارات store تستخدم PGlite محليًا مع تسلسل اتصالاته؛ GitHub CI يضيف PostgreSQL 18 فعليًا لاختبار تسابق نسخ متعددة والأقفال ومحاسبة البايتات والتخزين. بيانات PostgreSQL في CI مؤقتة وغير إنتاجية.
- اختبارات الصور تفحص streaming والذاكرة والإطارات، واختبارات الموسيقى تحتفظ بفحص البكسل الفعلي للشعار بدل تجاهل الصورة عند تغير mock.

حماية الهجمات الشبكية قبل وصولها للتطبيق تعتمد كذلك على طبقة المنصة. [Render يوثق حماية DDoS تلقائية للخدمات](https://render.com/docs/ddos-protection). هذه الدفعة تضيف حماية استهلاك التطبيق؛ لم تغير DNS أو تعدّ نظام WAF خاصًا، ولم تنفذ هجومًا أو اختبار إغراق على الإنتاج.
