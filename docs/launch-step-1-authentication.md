# الخطوة الأولى: أمان الدخول وإدارة الموقع

هذه الخطوة تنفذ محور الدخول والإدارة من مراجعة جاهزية 20 أكتوبر 2026. حماية الضغط وTLS وشبكة قاعدة البيانات والتعافي والسعة لها خطوات منفصلة؛ لا تُحسب منتهية بهذا التعديل.

## الضوابط المنفذة

1. حساب مدير نشط مع معرّف Discord صريح في ADMIN_DISCORD_IDS، أو بريد في ADMIN_EMAILS بشرط email_verified=true من موفر الهوية. لا يكفي البريد المعروض، أو عنوان غير مؤكد، أو حساب موقوف.
2. email_verified عمود جديد افتراضيه false للحسابات القديمة. لا نفترض تأكيد عناوين سابقة؛ يتحدث عند دخول جديد عبر Discord/Google. الربط بين الحسابين يحفظ هوية الحساب الأصلية ولا يدمج حسابين موجودين أو يستبدل Discord آخر.
3. تدوير معرف الجلسة بعد نجاح الدخول/الربط، وإتلاف الجلسة السابقة في المخزن، وحفظ الجديدة قبل إعادة التوجيه. لا تُنسخ بيانات جلسة عشوائية، وينشأ رمز CSRF جديد لاحقًا.
4. صلاحية بدء OAuth عشر دقائق، وربط التدفق بالجلسة والموفر، ومقارنة state آمنة، وتقييد returnTo لمسار داخلي. سجل قصير العمر يحفظ تجزئة state والجلـسة فقط؛ claim في PostgreSQL يمنع استهلاك التدفق مرتين حتى بالتوازي. تُحذف السجلات المنتهية عند بدء تدفق جديد.
5. أول ربط لهوية Discord جديدة إلى حساب Google يحتاج إثباتًا حديثًا للحساب الحالي. إن مضت أكثر من 15 دقيقة، يعود المستخدم إلى Google ثم يكمل الربط. لا يُربط حساب آخر بسبب تدفق قديم.
6. إدارة الموقع تحتاج إثبات دخول مرتبطًا بمعرّف الحساب وsubject الموفر: قراءة إدارية حتى أربع ساعات، وتعديلات إدارية حتى 15 دقيقة من الدخول. هذه مهلة مطلقة لا تمددها الطلبات. لا تتغير مهلة عمليات لوحة سيرفر العميل العادية بهذا الضابط.
7. عند انتهاء المهلة، يرجع الخادم ADMIN_REAUTH_REQUIRED قبل التعديل، وتعرض لوحة الإدارة رابط دخول. لا يعاد إرسال التعديل تلقائيًا؛ يراجعه المدير بعد عودته.
8. فحص صلاحية الحساب والإدارة في كل طلب. صفحات الإدارة وسكربتها محمية أيضًا. توقف الحساب أو زوال صلاحية المدير يوقف الطلب حتى لو كانت الجلسة حديثة.
9. تسجيل الخروج يدمر الجلسة ويمسح cookie. يستمر اشتراط CSRF ومصدر الطلب، وخصائص HttpOnly وSecure في الإنتاج وSameSite=Lax.
10. استجابات API وOAuth والإدارة تحمل no-store وVary: Cookie. التوكنات لا تعاد للواجهة، ولا تحفظ في إثبات الجلسة، وتستمر طبقة التشفير السابقة لتخزينها.
11. مهلة لاتصالات موفر الهوية، ورفض subject أو token أو expiry غير صالح. لا يرسل بريد ترحيب لعنوان غير مؤكد.

## تجربة المدير بعد التحديث

- الجلسة القديمة للعميل العادي تستمر. عند تسجيل الدخول التالي يتغير معرفها.
- جلسات الإدارة القديمة لا تحمل إثبات الدخول الجديد: يلزم تسجيل دخول واحد لاستئناف الإدارة.
- المدير المسموح بالبريد فقط يحتاج الدخول ليُثبت الموفر تأكيد بريده؛ لا تُمنح الصلاحية اعتمادًا على بيانات قديمة.
- رسالة إعادة التحقق لا تعني فشل الاشتراك أو فقد الحساب. لم ينفذ التعديل، ويجب مراجعته بعد الدخول.
- العودة عبر OAuth هي إعادة إثبات للهوية عند الموفر؛ لا ندّعي أنها تجبر الموفر على طلب كلمة مرور جديدة أو MFA. إدارة MFA في حسابات Discord/Google وRender/GitHub تظل ضابطًا تشغيليًا منفصلًا.

## الاختبارات

tests/authentication.test.js يشغّل Express وexpress-session عبر HTTP محلي وقاعدة PostgreSQL معزولة PGlite. موفرا الهوية محاكيان؛ لا تُستخدم بيانات أو توكنات عميل:

- بريد مؤكد وغير مؤكد وقيم تحقق غير منطقية وحساب موقوف.
- ربط الإثبات بالحساب والموفر، ومهلة القراءة والكتابة، ورفض الوقت المستقبلي.
- المسارات الخارجية والتحويلات المشفرة والأحرف غير المسموحة.
- تدوير cookie، رفض القديمة، إبطال CSRF القديم، وإتلاف الجلسة بالخروج.
- رفض مصدر خارجي/غياب CSRF قبل التعديل.
- بدء وربط Discord وGoogle دون فقد الحساب أو استبداله.
- منع تدفق من متصفح أو موفر آخر، انتهاء المهلة، واستهلاك متزامن واحد فقط.
- إعادة التحقق لا تعيد إرسال العمل، ورفض جلسة إدارة قديمة بلا إثبات.
- no-store وHttpOnly وSameSite، وعرض رابط إعادة الدخول في واجهة الإدارة.

يبقى تحقق إنتاج غير مدمر بعد النشر: صحة الخدمات، تنفيذ الترحيل الإضافي، رؤوس الحماية، رفض وصول مجهول، ورفض callback غير صحيح. لا تعادل هذه الإجراءات تجربة موافقة OAuth حقيقية من حساب جديد.

## الترحيل والتراجع

الترحيل إضافي: email_verified وoauth_login_attempts مع فهرس صلاحية؛ لا حذف حسابات أو جلسات جماعيًا. العودة إلى كود سابق لا تحتاج إسقاط الجدول أو العمود، لكنها تعيد الضوابط الأضعف؛ لذلك يفضّل إصلاح أمامي عند ظهور خلل.
